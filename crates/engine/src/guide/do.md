# Doing the work in stone

1. `stone task move <id> in-progress` marks the task taken, so the store shows who has it.
2. Reads can stay narrow: `stone get <id>` prints the task, `stone get <id>#<anchor>` one section, and `stone search "words"` finds the rest.
3. Edits fit the store as the work goes: `stone edit <id> --section <name> --text "..."`. Fields take `--set key=value`; lists take `a,b`, `+a`, `-a`.
4. `stone edit <id> --check-ac <n>` ticks an acceptance criterion as it passes. `stone edit <id> --note "<text>"` adds a dated bullet to `## Notes` without rewriting the section; the same text twice adds it once.
5. A new fact has an owner. The component or decision holds it, edited with `stone edit` or created with `stone new` and pointed at with `stone link`; the task does not.
6. In the code, a component is the way in: `stone code explain <component>` prints its entry points first (`path#Symbol`, where execution starts), then what it does with each component it uses (its `## Uses` bullets), its files and its dependencies; a folder works too. `stone code outline <file>` shows what a file declares before it is read. `stone code find <Name> --kind class --limit 1` finds one type by its exact name. `stone code entries` lists every entry point.
7. Many answers marked inferred mean the edges are name guesses. `stone code native` runs the language indexers found on PATH once (it installs nothing and says which it skipped), and a `note:` line on later answers tells when edits made its edges out of date. A later run indexes only the projects with changed files (`--repo <name>` for one repo, `--all` for everything), and moving a task to done starts one in the background.
8. Library docs are not in stone. A component's `libraries` list gives the library and version for Docs MCP `search_docs`.
9. When reality disagrees with the plan, the plan changes in the store the same day; `stone check` shows what broke.
10. Code someone else wrote has a reason: `stone why <path>[:line]` gives it, and `stone history <id>` gives the history of an item, and `stone timeline` lists recent commits, finished tasks, decisions and doc edits. `stone precedents <task>` lists finished tasks that made the same kind of change, with their files, so you can copy their pattern; `--component <id>` or `--role <role>` look up without a task.
11. `stone commit-msg` prints the `Refs:` trailer lines for the task in progress, which puts the task in the commit.
12. A task made by mistake or only to try something is deleted with `stone task remove <id>` (`--dry-run` shows the verdict first); stone refuses when another item links to it or a commit names it, and says which. A task that was real work and is no longer wanted stays in the store as `stone task move <id> archived`. Deleting task files by hand skips these checks and leaves broken links. `stone rename <id> <new-id>` gives a doc, plan, reference or architecture item a new id and rewrites its links; `stone delete <id>` is refused while items link to it. After a merge two files can share a number: `stone renumber <path>`.
