## Plan

Owner decision (2026-11-08): the store guard blocks writes to the store, not text that mentions it. Today `.claude/hooks/stone-guard.mjs` denies any shell command that names a store path unless the whole command starts with `stone` or `git`. So `S=target/debug/stone.exe; $S edit ... --set components=arch/x/stone/y` is denied, and so are Read, Grep and Glob on store files. About 5 denied commands in one session had no write in them.

1. Read, Grep and Glob: always allowed. Edit, Write and NotebookEdit on a store path (`stone/` or `.stone/`, as `STORE_PATH` matches today): still denied.
2. Bash and PowerShell: split the command into segments on `;`, `&&`, `||`, `|` and newlines. A segment is denied only when it writes to a store path:
   - a redirect (`>`, `>>`, `Out-File`, `Set-Content`, `Add-Content`, `tee`) whose target is a store path;
   - or a segment whose program is one of `cp`, `mv`, `rm`, `touch`, `mkdir`, `sed -i`, `perl -i`, `Copy-Item`, `Move-Item`, `Remove-Item`, `New-Item`, `Rename-Item` with a store path in its arguments.
   A segment whose program is `stone`, `stone.exe`, a path ending in either, a `$VAR` holding one, or `git` is always allowed. Everything else is allowed.
3. Keep the header comment: a nudge, not a security boundary. Keep the deny message.
4. Test choice: add. The hook is a decision with real branches and has no test. Add `.claude/hooks/stone-guard.test.mjs` using `node:test`, one table: it spawns the hook with a JSON input on stdin and asserts deny or allow. Rows: Read of a store file (allow); Edit of a store file (deny); `cat stone/tasks/CS-1.md` (allow); `echo x > stone/tasks/CS-1.md` (deny); `S=target/debug/stone.exe; $S edit CS-1 --set components=arch/a/stone/b` (allow); `cp a.md stone/docs/a.md` (deny); `git restore stone/config.yml` (allow); `ls; rm -rf .stone/index` (deny); `Set-Content stone/x.md 'a'` (deny); a command naming no store path (allow).
5. Run `node --test .claude/hooks/`, then the acceptance commands.
