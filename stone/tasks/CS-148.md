## Description

The owner accepts a task, sends it back with a comment, or changes its status from the task view and the task page. Each action is one locked file write through `PATCH /api/items/{id}`, so it shows in git like any CLI edit. See ADR-14.

## Plan

1. `crates/engine/src/edit.rs#Edit`: add `pub note: Option<String>`, documented as one line to add under `## Notes`. In `crates/server/src/write.rs#patch_item`, pass `body.note`. In `crates/cli/src/main.rs`, where `Edit` is built, pass `note: None`; the CLI gets no new flag, because `--section` already serves it.
2. `crates/engine/src/api.rs#PatchRequest`: add `note: Option<String>` with `ts(optional)`, documented as a line to add under `## Notes`. Run `cargo test -p carvestone-engine --features ts --test ts_export` to regenerate `web/src/api/types/PatchRequest.ts`.
3. `crates/engine/src/edit.rs`: add `fn add_note(body: &str, text: &str, day: &str) -> Result<String, EngineError>`. Replace each run of whitespace in `text`, newlines included, with one space, so a comment can never start a heading. Empty text after that gives `EngineError::Invalid("the note is empty; write what has to change")`. The line is `- {day}: {text}`. Read the current `Notes` section the way `replace_section` does. When it already holds that exact line, return `body` unchanged, so the same write twice gives no diff. Otherwise call `set_section` with the held text plus the line, or the line alone when the section is missing or empty.
4. `crates/engine/src/edit.rs#Repo::edit_if_match`: count `req.note` in the "nothing to change" check. After the `check_ac` step, apply `add_note` with `today()`. The `sync_closed` and `check_done_sections` steps stay after it.
5. Test choice: add `a_note_lands_under_notes_once` in `crates/engine/tests/features/tasks.rs`, because this is a new saved format. Table rows: no Notes section, an existing Notes section with text after it in another section, CRLF file, a comment holding a newline and `## x`, the same edit twice (no diff), and a blank comment (the error above). Expected text is literal. It catches a lost section, a broken heading and a repeat line. It misses the HTTP path, which step 6 covers.
6. Test choice: patch `a_patch_and_a_create_save_the_files_the_cli_would_write` in `crates/server/tests/features/main.rs`: send `{"set": {"status": "todo"}, "note": "Sent back: fix the title"}` to a task in `review`, and expect both changes in the one file. Add one row to the error table for a blank note, status 422 as the engine gives other invalid edits (read the status from `crates/server/src/error.rs` and use it). This is the send-back contract.
7. `web/src/api/client.ts`: give `request` an optional `RequestInit` and add `api.patch<T>(path, body)`, which sends `method: "PATCH"`, a JSON `Content-Type` and `JSON.stringify(body)`. The offline and error handling stay as they are.
8. Add `web/src/components/work/OwnerActions.tsx`. It exports `Decision({ item, onDone })` and `StatusPicker({ item, onDone })`, both on `ItemView`, sharing one local hook `useOwnerWrite(item, onDone)`. The hook uses `useMutation` to call `api.patch<PatchReply>(itemUrl(item.id), { ...request, if_match: item.etag })`. On success it runs `queryClient.invalidateQueries({ queryKey: ["items"] })` and then `onDone`.
9. `Decision` renders nothing unless `textField(item.fields, "status") === "review"`. Otherwise it renders, as on the Task board, `Button` "Accept" (default variant) and `Button` "Send back" (outline variant). Accept sends `{ set: { status: "done" } }`. Send back opens a form below the buttons with `basis-full`: a `textarea` labelled "What has to change", a "Send back" submit that is disabled while the text is blank, and a "Cancel" button. Submit sends `{ set: { status: "todo" }, note: `Sent back: ${text}` }`. A failed write shows the server's sentence with `ErrorNotice` under the buttons, and the view stays open.
10. `StatusPicker` renders a native `select` labelled "Status", with the options from `useConfig().data?.statuses.task`, the current status selected, and each option's text from `columnLabel`. Choosing one sends `{ set: { status } }`. It is disabled while the write runs. A failed write shows `ErrorNotice` under it.
11. `web/src/components/peek/TaskOverlay.tsx#TaskOverlay`: in the header, before "Open full page", render `Decision` when `view` is loaded, with `onDone={onClose}`. In `Facts`, add a first `Fact` labelled "Status" holding `StatusPicker` when `item` is loaded, and pass `onClose` down as `onDone`. Closing is right because `row` is a snapshot and would show the old status.
12. `web/src/components/work/TaskPage.tsx#Task`: in the "Status" `Fact`, render `StatusPicker` after the badges, and render `Decision` below the `dl`, both with an empty `onDone`; the invalidation refreshes this page.

It misses the look, which step 15 covers.
