## Description

Reported once: `stone code outline` failed with `FOREIGN KEY constraint failed` (error code 787) right after a `code_roots` change and a `stone edit`, then passed on retry. Two stone processes can run the code pass on one index at the same time, and one can delete rows the other is about to point at. After this change only one process runs the code pass; a read that starts meanwhile waits for it and never fails because of it.

## Plan

Cause: likely, not proven. The Lead could not get error 787: about 230 parallel `stone code outline` runs in a throwaway repo, after new code roots of 2500 to 3000 files, gave no foreign key error and one `database is locked: Error code 5`. So step 1 is the repro, and no fix starts before it fails.

What the code shows:

- Every CLI read refreshes the index first: `crates/engine/src/code.rs#open` calls `crates/engine/src/refresh.rs#refresh_in`, which runs `crates/engine/src/code_index.rs#refresh_code`. Nothing stops two processes from running that pass at once.
- `crates/engine/src/code_index.rs#finish` reads all row ids once (`load_world`) and writes later, in many separate transactions (`ensure_buckets`, then `sync_edges` in batches, then `sync_buckets`). The index has `foreign_keys` on (`crates/index/src/lib.rs#configure`), so a write that names a row another process deleted meanwhile fails with error 787.
- Most likely path: process A commits new bucket rows in `ensure_buckets`. Process B ends its own pass in `sync_buckets`, which deletes every bucket that no edge points at yet, A's new ones included. A then inserts edges with those `dst_bucket` ids in `sync_edges`.
- Second path, same result: B replaces a file (`write_file` calls `forget`) after A's `load_world`; A then writes edges with the old `file_id` and `src_id`.

The fix closes both paths: one code pass at a time across processes. A second process waits for the first, then re-reads and finds nothing left to do (the crew rule for writes: take the lock first, then re-read, compute and save).

Steps:

1. Repro (debug, tdd), in `crates/engine/tests/features/code_graph.rs`: add `concurrent_reads_after_new_code_all_answer`.
   - Store: `project(&[])`. Import `carvestone_engine::refresh::refresh_batched` and `std::thread`.
   - 4 rounds, `r` from 0 to 3. Each round first writes 120 files `src/r{r}/f{i}.py` (`i` from 0 to 119, `k = i % 60`) with the text `class C{r}_{i}:\n    def go{r}_{k}(self, o):\n        return o.go{r}_{(k + 1) % 60}(self)\n`. Each method name has two declarations, so every call needs a bucket.
   - Then `thread::scope` with 8 threads (pattern: `concurrent_writes_all_land` in `crates/engine/tests/features/items.rs`). Each thread makes its own `store.repo()`, calls `refresh_batched(&repo, 5, None)`, then `outline(&repo, &query("src/r0/f0.py"))`, and returns both results. The batch size 5 makes the threads write in turns, so each pass holds a part of the files.
   - After the scope: assert every result is `Ok` (print the error text on failure), and that `find(&repo, &query(&format!("C{r}_0")))` has exactly 1 hit.
   - Run it 5 times: `cargo test -p carvestone-engine --test features code_graph::concurrent_reads`. Red means at least one run fails with `FOREIGN KEY constraint failed` or `database is locked`. Write the error text of the red run in `## Notes`.
   - All 5 runs green: stop. Write the 5 results in `## Notes` and change no other file.
   - Test choice: Add. Closest existing test: `a_changed_file_shows_in_the_next_query` in the same file; it has one reader, so a patch cannot reach a race. Catches: a read that fails while other passes write. Misses: two processes with different stone versions.
2. `crates/index/src/lib.rs`: add `pub struct PassLock` (one private field, the lock file's `Connection`) and `PassLock::take(index: &Path, wait: Duration) -> Result<Option<PassLock>, IndexError>`. Copy `crates/index/src/rebuild.rs#Lock`: open `index.with_extension("pass.lock")`, set `busy_timeout(wait)`, run `BEGIN EXCLUSIVE`. A busy or locked failure (`ErrorCode::DatabaseBusy`, `ErrorCode::DatabaseLocked`) returns `Ok(None)`; any other failure is `Err`. The doc comment says why SQLite holds it: the lock goes when the process ends, so a crash leaves none behind. Its own file, not `index.lock`: a rebuild must not wait for a pass.
3. `crates/engine/src/refresh.rs`: add `const PASS_WAIT: Duration = Duration::from_secs(60);` with a comment: the longest a read waits for another process's code pass.
4. `crates/engine/src/refresh.rs#refresh_now`: before the call of `refresh_code`, call `PassLock::take(&repo.store.layout.index_path(), PASS_WAIT)?` and keep the value until after `recompute_if_stale`. When it is `Some`: run `refresh_code`, `code_native::restore` and `modules::recompute_if_stale` as now. When it is `None`: skip those three calls and leave `code_changed` at 0; the other process set `code_building`, so code queries already print the `code index is still building` note (`crates/engine/src/code_index.rs#building_note`). The item-file batches before it and `refresh_git` after it stay outside the lock.
5. Green: the test of step 1 passes 5 times in a row. If a run still fails, stop and write the error text in `## Notes`.
6. No change to `crates/engine/src/code_index.rs`, the CLI, MCP or the web UI: none. `refresh_code` has one caller, `refresh_now` (`stone code uses refresh_code`).
