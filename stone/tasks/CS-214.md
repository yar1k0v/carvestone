## Description

A --root that holds no store walks up to an ancestor, so a write lands in the wrong store. A review run added a code root to this repo's config that way. An explicit --root must be used as given, and fail when it holds no store. See crates/store/src/layout.rs.

## Acceptance criteria

- [x] `cargo test -p carvestone-cli` → exits 0, `0 failed`, and the new test passes
- [x] `cargo clippy --workspace --all-targets -- -D warnings` → exits 0

## Plan

`--root` is documented as the repository root, so it must be used as given. Walking up stays for the current directory, when no `--root` is given. `Layout::discover` does not change.

1. In `crates/cli/src/main.rs`, add `open_repo(cli_root: Option<&Path>, start: &Path) -> anyhow::Result<Repo>`. With a `--root` whose folder has no `stone/config.yml`, it fails with: `<path> holds no store; run stone init there, or pass the repository root`. Otherwise it calls `Repo::open(start)`.
2. Use it at both `Repo::open` calls in `crates/cli/src/main.rs#run`: the `Instructions` write branch and the main one. `init` and the guide print stay as they are.
3. Test choice: add. A write landing in the wrong store is a bug no existing test reaches. In `crates/cli/tests/features/main.rs`, one table test with a store and a subfolder of it. Rows: `--root` on the subfolder with `config add-code-root`, `new task` and `get` all exit 1 and name the path; the store's config file and task list stay the same. One passing row: `--root` on the store itself. One row: no `--root`, run from the subfolder, still finds the store.
4. If an existing test passes a subfolder as `--root`, stop and report it under `## Notes`.
5. Run `cargo build --bin stone`, then the acceptance commands.

## Outcome

An explicit --root now fails with a message naming the folder when it holds no store, instead of writing into a parent store; no --root still walks up. Checked by a new CLI table test, cargo test -p carvestone-cli (0 failed) and clippy.
