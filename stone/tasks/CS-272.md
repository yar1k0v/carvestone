## Description

When git merges two branches that both changed a stone item, stone merges the item by paragraph and by front matter field, not by line. Only edits to the same paragraph or the same field stay a conflict.

## Plan

1. `crates/core/src/section.rs#blocks` (new): `pub fn blocks(body: &str) -> Vec<&str>`. Split `body` into units built on `scan`: a heading line is one unit; a fenced block from its opening to its closing line is one unit; any other run of lines up to a blank line is one unit. Each unit keeps its trailing blank lines, so concatenating all units gives `body` exactly. Catches: a fence with blank lines split in two. Misses: nothing beyond the scanner. Test: add `blocks` unit test in `section.rs` with one table: empty body, heading plus paragraph, two paragraphs, fence holding a blank line, CRLF body; each row asserts the unit list and that the join equals the input.
2. `Cargo.toml` `[workspace.dependencies]`: add `similar = "2"`; `crates/engine/Cargo.toml`: `similar.workspace = true`. Docs: https://docs.rs/similar/latest/similar/fn.capture_diff_slices.html (use `Algorithm::Myers`, read `DiffOp` ranges).
3. `crates/engine/src/merge.rs` (new), `pub mod merge;` in `crates/engine/src/lib.rs`. `pub struct Merged { pub text: String, pub conflicts: usize }` (new). `pub fn merge_text(base: &str, ours: &str, theirs: &str) -> Merged` (new). Split each input into front matter (`carvestone_store::frontmatter::Document::parse`, body from `Document::body_line`) and body; a side whose front matter does not parse makes the whole file one conflict.
4. Body merge in `merge.rs#merge_body` (new): units from `blocks`. Diff base→ours and base→theirs with `similar::capture_diff_slices`. Turn each into hunks `(base range, new units)`. Walk both hunk lists by base position: a hunk on one side only is applied; two overlapping hunks with equal new units are applied once; two pure insertions at the same base position are both applied, ours first; any other overlap is a conflict.
5. A conflict writes, in place of the overlapping units: `<<<<<<< ours`, the ours units, `=======`, the theirs units, `>>>>>>> theirs`, each marker on its own line with the line ending of ours (`section::eol`). Each conflict adds 1 to `conflicts`.
6. Front matter merge in `merge.rs#merge_front` (new): per key of the union of the three mappings, in ours key order then new theirs keys. Changed on one side: take that side. Both changed to the same value: take it. Both changed and both are sequences: take ours, then add theirs items missing from ours, then drop items removed on either side from base. Key `generated`: take ours. Any other both-changed key: the whole front matter becomes one conflict (markers around ours front matter and theirs front matter). Write the result from the ours `Document` with `Document::set` and `Document::to_text`, so untouched lines keep their bytes.
7. `crates/cli/src/main.rs#Command::MergeFile` (new): `stone merge-file <BASE> <OURS> <THEIRS> <PATH>`, the git merge driver arguments `%O %A %B %P`. Read the 3 files, call `merge_text`, write `text` to OURS, exit 0 when `conflicts == 0`, else print `✗ <PATH>: <n> conflicts` and exit 1. Test: none (smoke via acceptance `--help`; logic covered by the engine table).
8. Test: add `crates/engine/tests/features/merge.rs` (new), `mod merge;` in `crates/engine/tests/features/main.rs`. Patch was not possible: no merge test exists. One table test `merge_table` with rows (base, ours, theirs, expected text, conflicts): no change; ours only edits P1; ours edits P1 and theirs edits P3; both edit P1 differently (1 conflict, exact markers); both edit P1 the same; both append at the end (ours then theirs); fence with a blank line edited on one side; CRLF input keeps CRLF; front matter `links` added on both sides (union); front matter `status` changed on both sides (1 conflict); unparsable front matter on one side (1 conflict). Second test `merge_is_identity`: for each table row, `merge_text(b, b, x) == x` and `merge_text(b, x, b) == x`. Expected values are literals.
