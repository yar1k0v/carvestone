## Description

Stone has C4 diagrams in docs (context, container, component, dynamic), architecture items (system, container, component), a service view and the code graph (explain, outline). It has no stated split between a high-level design (what the product is made of and how the parts talk) and a low-level design (how one part works inside), so a reader cannot ask for either. Goal: a reader opens one place per level and sees it, kept true by the code. Start with a short design: which views make HLD (for example context, containers, run-time connections, topics) and which make LLD (for example components of one service, key flows as dynamic diagrams, modules and classes from the code graph), where each lives (doc, architecture item, generated), what the web UI and CLI show per level, and what is drawn by hand versus derived from code. The design is a decision for the product owner before building. Builds on CS-83, CS-84, CS-92 and CS-93.

## Acceptance criteria

- [x] A decision records what HLD and LLD mean in stone and where each is shown
- [x] The web UI offers an HLD view and an LLD view of a service, reached from each other
- [x] The CLI prints each level for a component or service
- [x] stone check reports when a hand-drawn view disagrees with the code
- [x] cargo test --workspace and the web checks pass

## Outcome

Stone now names the two design levels and shows both. ADR-13 records what HLD and LLD mean. A doc can say level: hld or level: lld, and stone check rejects other values and warns when a flow doc or diagram names code that is gone. stone arch hld and stone arch lld <container> print each level in the CLI. In the web UI the Architecture page opens on an HLD and LLD switch: the HLD lists systems, containers, how they connect and the docs marked hld, a container opens its low-level design (the service page with the docs marked lld and their start points), and the low-level design links back to the HLD.
