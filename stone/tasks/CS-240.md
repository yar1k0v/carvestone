## Description

Follow-up of CS-233. The ready check gates `stone task move <id> in-progress` only. `stone edit <id> --set status=in-progress` and the server PATCH of an item (the web UI) change the status through the edit path and skip the check. This task gates that path too: `--force` on `stone edit`, a `force` field on the PATCH request, and a web status picker that lists the gaps and offers the override.

## Plan

Decisions (Lead, run mode): the gate judges the edited document, so one edit that sets `components` and the status passes when the result is ready. A dry run is refused the same way. The web UI detects the refusal by the text of the message; the error body stays as it is.

The refusal sentence today, from `crates/engine/src/edit_tasks.rs#move_task`: the task label, ` is not ready for in-progress: `, the gaps joined with `; `, then `; fix them, or run stone task move <label> in-progress --force`.

1. `crates/engine/src/ready.rs`: add `refuse_unready` (new), `pub(crate)`. It takes the repo, the task label, the item and the override command, calls `crates/engine/src/ready.rs#gaps`, and with one or more gaps returns `EngineError::Invalid` with the sentence above, where the text after `or run ` is the override command it was given. No gap: `Ok(())`.
2. `crates/engine/src/edit_tasks.rs#move_task`: call `refuse_unready` with the override command `stone task move <label> in-progress --force` in place of its own gap code. The message stays the same, byte for byte.
3. `crates/engine/src/edit.rs#Edit`: add the field `pub force: bool`. The struct derives `Default`, so callers that use `..Edit::default()` do not change.
4. `crates/engine/src/edit.rs#edit_if_match`: inside the closure, after the `sync_closed` call. When the item is a task, the new status is `in-progress`, the status before the edit was not `in-progress`, and `force` is false: build the item from the edited document with `item_from_document` (already imported there) and call `refuse_unready` with the override command `stone edit <label> --set status=in-progress --force`. The check runs under the lock on the re-read entry.
5. `crates/cli/src/main.rs#EditArgs`: add `#[arg(long)] force: bool` with the doc comment `/// Set the status to in-progress although the ready check finds gaps.` Pass it into the `Edit` literal in `crates/cli/src/main.rs#run`.
6. `crates/engine/src/api.rs#PatchRequest`: add `force: bool` with the same serde and ts attributes as its `dry_run` field. Pass it into the `Edit` literal in `crates/server/src/write.rs#patch_item`.
7. Run the `ts_export` test; it rewrites `web/src/api/types/PatchRequest.ts`. No other generated file may change.

The same edit with `force: true` writes `status: in-progress`. One edit on a task that lacks only `components`, setting `components` and the status together, writes the status.
