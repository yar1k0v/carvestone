## Description

The accepted context board needs people, outside systems and one product box. Arch items have only system, container and component. Add what level 1 needs, so a product with several systems shows one box. Runs before the C4 generation task.

## Plan

The owner chose one `kind` field and a parent system (ADR-20). `Fields.kind` already exists and `stone edit --set` already writes it, and `parent` has no type rule today. No new item type, no id change, and existing stores stay valid. This task adds the rules and carries the value. Generated diagrams are CS-207.

1. In `crates/core/src/item.rs`, add `pub const SYSTEM_KINDS: [&str; 2] = ["person", "external"]` and `pub const CONTAINER_KINDS: [&str; 1] = ["store"]`, beside `LEVELS` if that is where the vocabulary lists sit, and export them from `crates/core/src/lib.rs`.
2. In `crates/engine/src/check_fields.rs#field_problems`, add a `kind` rule for arch items, in the style of the `level` rule: a system takes `SYSTEM_KINDS`, a container takes `CONTAINER_KINDS`, a component takes none. The message names the allowed values.
3. In the same function, add a `parent` rule: a system's `parent` must resolve to a system, and neither a system with a `kind` nor its parent may be a child in a product. So a `person` or `external` system has no `parent`, and a system with a `kind` is never a `parent`. A `parent` that does not resolve stays with the existing link rule.
4. In `crates/engine/src/api_config.rs#fields_of`, add `spec("kind", "text")` to the System, Container and Component row.
5. Add `kind: Option<String>` to `crates/engine/src/design.rs#Part` and `crates/engine/src/arch_graph.rs#ArchNode`, with the same serde and ts attributes as their other optional fields, filled from `item.fields.kind`. If the ts bindings are generated into `web/`, regenerate them the way the repo does, and add nothing else under `web/`.
6. In `crates/cli/src/main.rs`, where `stone arch hld` prints a part's technology, also print its kind.
7. In `crates/engine/src/arch_gaps.rs#gaps`, skip `NoCode` and `NoDoc` for a node with kind `store`. A store still gets `NoConnection`.
8. In `crates/engine/src/guide/design.md`, in step 2, add: a person or outside system is a system with `stone edit <id> --set kind=person` or `kind=external`; a data store or message bus is a container with `kind=store`; a product with several systems is one system set as their `parent`. Keep the six steps.
9. Test choice: add. New check rules with real branches and a saved field. In `crates/engine/tests/features/architecture.rs`, one table test for every wrong `kind` and `parent` case in steps 2 and 3, with one valid store as the clean row. It catches a kind on the wrong type, and misses nothing a reader sees.
10. Test choice: patch. Add a store with no code and no doc to the gaps fixture, and assert only its absence from `NoCode` and `NoDoc`. Add the kind to the `hld` assertion in `hld_shows_the_systems_containers_connections_and_marked_docs`.
11. Run `cargo build --bin stone`, then the acceptance commands.

## Outcome

Arch items now take an optional kind: person or external on a system, store on a container; stone check refuses a wrong kind, a parent on a person or outside system, and a kind system used as a parent. hld, the map and arch hld carry the kind, and a store is not a no-code or no-doc gap. Checked with architecture:: (15 passed), guide:: (2 passed), clippy, workspace tests and stone check.

## Notes

- Outside the plan: the table test has no row for a system under a kinded system. The container row reaches the same branch, and QA saw the system case refused.
