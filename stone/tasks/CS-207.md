## Description

stone arch c4 and the server generate the C4 context, container and component diagrams as mermaid text, from arch items and connections. The web pages move to it in CS-196.

## Acceptance criteria

- [x] `cargo test -p carvestone-engine --test features c4::` → exits 0, `0 failed`, and more than 0 passed
- [x] `pnpm --dir web test` → exits 0, `0 failed`
- [x] `cargo clippy --workspace --all-targets -- -D warnings` → exits 0
- [x] `target/debug/stone.exe arch c4 container` → prints `C4Container` with this repo's containers

## Plan

Stone generates mermaid C4 text from arch items. `web/src/components/c4/C4View.tsx` already draws that text, so no new diagram format exists, and an agent reads the same output. The web pages change in CS-196, not here. ADR-20 is the rule: agents edit data, never layout.

1. Add `description` and `technology` (optional, same attributes as `kind`) to `crates/engine/src/arch_graph.rs#ArchNode`. Add `technology` to `#UsesEdge`, from the `## Uses` bullet, beside `description`. Regenerate the ts bindings the way CS-211 did.
2. Add `crates/engine/src/arch_c4.rs` with `pub fn c4_context(repo: &Repo) -> Result<String, EngineError>`, `pub fn c4_container(repo: &Repo, system: Option<&str>) -> Result<String, EngineError>` and `pub fn c4_component(repo: &Repo, container: &str) -> Result<String, EngineError>`, all built from `arch_graph`. Add the module to `crates/engine/src/lib.rs`.
3. The focus of a store is each system with no `parent` and no `kind`. Walk `parent` with a visited set, because `stone check` allows a loop: a repeated id ends the walk.
4. A connection between two descendants is lifted to the boxes the level draws. A connection inside one box is dropped. One line per direction and pair: a connection written at that level wins, otherwise the distinct phrases are joined with `, ` in id order. The technology is joined the same way.
5. `c4_context` writes `C4Context`, or the same with several focus systems as a landscape. `title System context diagram for <name>`, or `System landscape diagram` for several. `Person` for `kind: person`, `System_Ext` for `kind: external`, `System` for a focus system. Each box has `$link="<id>"`.
6. `c4_container` writes `C4Container`. `system` may be omitted only with one focus system; with several, refuse and name them. `title Container diagram for <name>`. A `System_Boundary` holds every container below the focus system, `ContainerDb` for `kind: store`, else `Container`, each with its `technology` and `description`. Outside the boundary, draw the people, outside systems and other focus systems that have a line to it.
7. `c4_component` writes `C4Component`. `title Component diagram for <name>`. A `Container_Boundary` holds its child components. Outside it, draw the parts with a line to it. A written connection keeps its phrase and technology. A code edge with no written connection gets the label `<n> references`, with no technology. An `inferred_only` edge is left out.
8. Order boxes and lines by id. Same store, same text. Write a `"` in a value as `#quot;`, which is mermaid's own entity, and decode it in `unquote` in `web/src/components/c4/parse.ts`. Add a row for it to the test in step 13.
9. In `crates/cli/src/main.rs`, add `arch c4 [context|container|component] [<id>]`, default `context`, printing the text. With `--json`, print `{ "source": <text> }`. Add it to `CLI_NESTED` in `crates/engine/src/guide.rs`.
10. In `crates/server/src/lib.rs` and `routes.rs`, add `/api/arch/c4/context`, `/api/arch/c4/container` with optional `?system=` and `/api/arch/c4/component/{*id}`, returning `{ source }`, in the style of `routes::arch_hld`. `cache.rs` already covers `/api/arch/`.
11. In `crates/engine/src/guide/overview.md`, change the Diagrams line: context, container and component diagrams come from arch items through `stone arch c4`, and only `C4Dynamic` is written in a doc. Add `stone arch c4` to step 6 of `crates/engine/src/guide/design.md`, keeping six steps.
12. Test choice: add. New public behavior and an output format. Add `crates/engine/tests/features/c4.rs` with one fixture: a product with two child systems, a person, an outside system, a store and connections across the children. Assert each level's whole text, written by hand. It catches a wrong lift and a line inside one box. Rows for a parent loop, several focus systems and an unknown id go in one table test.
13. Test choice: add. In `web/src/components/c4/c4.test.tsx`, parse the three texts from step 12 with `parse.ts` and assert element and line counts, so the two sides agree.
14. Run `cargo build --bin stone`, then the acceptance commands.
