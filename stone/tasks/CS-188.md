## Description

stone new and stone edit accept any text for `stale_after` and `created`, so `--set stale_after=soon` writes a value no stale check can read, and `--set created=soon` writes one that `stone check` then reports. Both are refused on write with one date rule, and `stone check` reports a bad `stale_after` written by hand. Found while reviewing CS-187 and confirmed by dry runs on 2026-11-06 and 2026-11-11.

## Plan

Cause: `crates/engine/src/fields.rs#set_scalar` saves any text for `stale_after` and `created`; only `status`, `kind` and `priority` have a rule there (`#check_vocab`). `stone new --set`, `stone new --from`, `stone edit --set` and the server and MCP edits all reach it through `crates/engine/src/fields.rs#apply_set`. `crates/engine/src/check_fields.rs#field_problems` tests `created` and the stamps with `#is_date`, never `stale_after`, so `stone check` is silent on it. `crates/engine/src/stale.rs#day_of` then reads no day from the value, and the item is never stale. Reproduced on a scratch store: `--set stale_after=soon`, `=2020-13-45`, an empty value and `--set created=soon` all exit 0.

The accepted form is the one `is_date` already defines: `YYYY-MM-DD` with a real day, alone or followed by `T` and a time. So a plain date and a full timestamp with a UTC offset both pass. The text after `T` is not judged here; CS-235 makes `is_date` strict, in that one function, for the write rule and for check together.

1. In `crates/engine/src/check_fields.rs`, change `fn is_date` to `pub(crate) fn is_date`. Change nothing else in it.
2. In `crates/engine/src/fields.rs`, add `use crate::check_fields::is_date;`. In `#set_scalar`, in the `else` branch after the `check_vocab` call, add: when `key` is `"stale_after"` or `"created"` and `!is_date(value)`, return `EngineError::Invalid` with exactly this text, where `{value}` is the trimmed value: ``{key} `{value}` is not a date; use YYYY-MM-DD or a timestamp such as 2026-12-01T09:30:00+00:00, or remove it with --unset {key}``. An empty value takes the same path. `closed` gets no rule. The `created` that `crates/engine/src/new_item.rs#build_text` sets itself comes from `crates/engine/src/create.rs#today` and passes.
3. In `crates/engine/src/check_fields.rs#field_problems`, directly after the `created` block, add the same block for `fields.stale_after`: when the value is not `is_date`, push `Problem::new(path, line_of("stale_after"), "date", ...)` with the text ``stale_after `{value}` is not a date; use YYYY-MM-DD``. It applies to every item type. Leave the `created` block as it is.
4. Seam: writes. Test choice: patch `errors` in `crates/engine/tests/features/items.rs`. It catches a refused value that still reaches the file. It misses the CLI wiring, which criteria 3 and 4 cover. Add these rows to `cases` (raise the array length), each expecting the error to contain ``<key> `<value>` is not a date``:
   - `repo.edit("CS-1", &set("stale_after", "soon"), false)`
   - `repo.edit("CS-1", &set("stale_after", "2026-13-45"), false)`
   - `repo.edit("CS-1", &set("stale_after", "5d"), false)`
   - `repo.edit("CS-1", &set("stale_after", "2026-12-01 09:30"), false)`
   - `repo.edit("CS-1", &set("stale_after", ""), false)`, expecting ``stale_after `` is not a date``
   - `repo.edit("CS-1", &set("created", "soon"), false)`, expecting ``created `soon` is not a date``
   - `repo.edit("CS-1", &set("created", ""), false)`, expecting ``created `` is not a date``
   - `repo.create(&NewItem { set: vec![("stale_after".into(), "soon".into())], ..new("doc", "Dated", None) }, false)`
   - `repo.create(&NewItem { set: vec![("created".into(), "soon".into())], ..new("doc", "Born", None) }, false)`, expecting ``created `soon` is not a date``
   - `repo.create(&NewItem::from_markdown("doc", "---\ntitle: Filed\nstale_after: soon\n---\n\nText.\n", "filed").unwrap(), false)`
   After the loop, beside the two existing assertions, add `assert!(!store.exists(...))` for `stone/docs/dated.md`, `stone/docs/born.md` and `stone/docs/filed.md`.
5. Same seam, the accepted forms. Test choice: patch `from_markdown_keeps_stale_after_and_names_what_it_left_out` in the same file. Its first row already proves the plain date. Add one row: name `"timestamp"`, source `"---\ntitle: Stamped\nstale_after: 2026-01-01T09:30:00+00:00\n---\n\nText.\n"`, stale line `Some("stale_after: 2026-01-01T09:30:00+00:00")`, warnings `vec![]`. It catches a rule that refuses the form with a UTC offset. `created` takes the same branch and the same `is_date`, and every `create` in the file already proves that a plain `created` passes, so it gets no row of its own; criterion 5 covers its timestamp form.
6. Seam: `stone check`. Test choice: patch `problems` in `crates/engine/tests/features/check.rs`. It catches a bad value written by hand, which step 2 never sees. Write `stone/docs/dated.md` as `"---\ntype: doc\ntitle: Dated\nstale_after: soon\n---\n"` before `store.git_track()`, and add this row to `want` directly before the `stone/docs/misfiled.md` row: ``stone/docs/dated.md:4: date: stale_after `soon` is not a date; use YYYY-MM-DD``. In `healthy` in the same file, change the `stone/docs/setup.md` text to `"---\ntype: doc\ntitle: Setup\nstale_after: 2999-01-01T00:00:00+00:00\n---\n\n## Overview\n\nText.\n"`, so `a_healthy_store_has_no_problems` proves that check accepts a timestamp.
7. Red first: add the rows of steps 4 and 6 before steps 2 and 3, and see them fail. The row of step 5 and the `healthy` change pass before and after: prove them once by making `is_date` return `false` for a value longer than 10 bytes, see both fail, and undo it.
