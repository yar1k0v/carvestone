A comment in `crates/engine/src/guide.rs` says a CLI test checks the guide command lists against the parser, but no such test exists. A command added to the CLI and not to the lists goes unnoticed, and `stone check` then warns on a guide that names it. This task adds that test.

## Plan

The parser is `crates/cli/src/main.rs#Cli`, a clap derive type, so `clap::CommandFactory` gives its command tree. The lists are `crates/engine/src/guide.rs#CLI_COMMANDS` and `crates/engine/src/guide.rs#CLI_NESTED`. Today both match the parser: 26 commands, and the subcommands of `arch` (6), `task` (5) and `config` (2). clap adds a `help` subcommand at each level; the test leaves it out.

1. In `crates/cli/src/main.rs`, add a `#[cfg(test)] mod tests` at the end of the file with one test, `crates/cli/src/main.rs#the_guide_lists_match_the_parser` (new). Test choice: add, because no existing test reads the parser, and the lists decide which commands `stone check` accepts in a guide.
2. The test builds `Cli::command()` and compares two things, each as a sorted list of names with `assert_eq!`:
   - the names of the top-level subcommands, without `help`, against `CLI_COMMANDS`;
   - for each parent that `CLI_NESTED` names, the names of that parent subcommands, without `help`, against the children `CLI_NESTED` lists for it.
   A parent with subcommands that `CLI_NESTED` does not name, such as `code`, is not compared: the guide checker does not judge its subcommands either.
3. Prove the test can fail, since the code it checks already exists. Remove `("task", "check")` from `CLI_NESTED` by hand, run the test and see it fail on the assertion, then put the entry back. Do the same once with one entry of `CLI_COMMANDS`. `crates/engine/src/guide.rs` must show no diff at the end.
4. Run the acceptance commands.
